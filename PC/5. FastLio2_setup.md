## 1. What FAST-LIO2 is, and which repo

FAST-LIO2 is LiDAR-inertial odometry: it fuses a 3D point cloud with an IMU to produce a 6-DoF pose at LiDAR rate. No loop closure, no global optimisation — it is odometry, not SLAM.

**Repo naming is confusing.** `hku-mars/FAST_LIO` contains **FAST-LIO2**; the 2021 and 2022 papers share one repository and the second superseded the first in place. The reliable check: **if it has an `ikd-Tree` submodule, it is FAST-LIO2.**

Not to be confused with sibling projects that do exist and are not this:

| Repo | What it is |
|---|---|
| `hku-mars/FASTER-LIO` | Different algorithm (iVox instead of ikd-Tree) |
| `hku-mars/FAST-LIVO` / `FAST-LIVO2` | Adds a camera — LiDAR-inertial-**visual** |
| `hku-mars/Point-LIO` | Different formulation, for aggressive motion |

FAST-LIVO2 is interesting eventually given the ZED, but it needs tight camera–LiDAR time sync and is substantially more setup.

**We used `Ericsii/FAST_LIO`** — the most active ROS 2 Humble port.

```bash
cd /ouster_ws/src
git clone https://github.com/Ericsii/FAST_LIO.git
cd FAST_LIO && git submodule update --init   # ikd-Tree
```

## 2. Trap: `livox_ros_driver2` is a hard dependency

FAST-LIO2 was written for Livox sensors. The Livox code paths are compiled in unconditionally, so the package will not build without the Livox message definitions **even though we have no Livox hardware**.

```
CMakeLists.txt:62: find_package(livox_ros_driver2 REQUIRED)
package.xml:30:    <depend>livox_ros_driver2</depend>
src/preprocess.h:5:       #include <livox_ros_driver2/msg/custom_msg.hpp>
src/laserMapping.cpp:62:  #include <livox_ros_driver2/msg/custom_msg.hpp>
```

Two routes. **Take the patch route.** The SDK route is documented below only as a warning.

### 2.1 The route that cost us the workspace — do not take it

Installing `livox_ros_driver2` requires Livox-SDK2, and the package has no plain `package.xml` (only `package_ROS1.xml` and `package_ROS2.xml`), so it ships a `build.sh` that selects one.

**`build.sh` runs colcon from the workspace root with no package selection.**

It did not build only itself. It started rebuilding `ouster_ros`, `ouster_sensor_msgs` and `agv_bringup`, then failed on the missing SDK library and **aborted `ouster_sensor_msgs` mid-build**, leaving:

```
install/
  agv_bringup
  livox_ros_driver2     ← stub
  (ouster_ros and ouster_sensor_msgs GONE)
```

The working LiDAR install was destroyed. Worse, `build.sh` had built without `--symlink-install`, leaving real directories in `build/`, which then blocked a clean rebuild:

```
failed to create symbolic link '.../ouster_sensor_msgs' because
existing path cannot be removed: Is a directory
```

**Recovery:**

```bash
cd /ouster_ws
rm -rf build/ouster_sensor_msgs build/ouster_ros \
       install/ouster_sensor_msgs install/ouster_ros
rm -rf src/livox_ros_driver2
colcon build --packages-select ouster_sensor_msgs ouster_ros agv_bringup --symlink-install
```

81 seconds to recompile `ouster_ros`. Nothing irreplaceable was lost — `build/` and `install/` are generated, and all real work lives in `src/` — but it cost twenty minutes mid-session.

> **Rule: never run a third-party build script inside a workspace containing work you care about.** Clone it into a throwaway workspace and merge the artifacts. This is the same family as the `src`-vs-`install` and bind-mount traps: a tool operating on wider scope than assumed.

### 2.2 The route that works — patch Livox out

Four categories of edit. Line numbers are for `Ericsii/FAST_LIO` as of 2026-09-16.

```bash
cd /ouster_ws/src/FAST_LIO

# 1. build files
sed -i 's/^find_package(livox_ros_driver2 REQUIRED)/# &/' CMakeLists.txt
sed -i 's/^\( *\)livox_ros_driver2$/\1# livox_ros_driver2/' CMakeLists.txt
sed -i 's|<depend>livox_ros_driver2</depend>|<!-- & -->|' package.xml

# 2. includes
sed -i 's|^#include <livox_ros_driver2/msg/custom_msg.hpp>|// &|' \
    src/preprocess.h src/laserMapping.cpp

# 3. single-line declarations — LATER FIRST so line numbers do not shift
sed -i '1140s|^|// |' src/laserMapping.cpp   # sub_pcl_livox_ member
sed -i  '923s|^|// |' src/laserMapping.cpp   # subscriber creation
sed -i  '176s|^|// |' src/preprocess.h       # avia_handler decl
sed -i  '161s|^|// |' src/preprocess.h       # process() overload decl

# 4. function bodies — LATER FIRST
sed -i '349a */' src/laserMapping.cpp        # end of livox_pcl_cbk
sed -i '310a /*' src/laserMapping.cpp        # start of livox_pcl_cbk
sed -i '195a */' src/preprocess.cpp          # end of avia_handler
sed -i  '94a /*' src/preprocess.cpp          # start of avia_handler
sed -i  '52a */' src/preprocess.cpp          # end of Livox process()
sed -i  '46a /*' src/preprocess.cpp          # start of Livox process()
```

**Finding the body boundaries** — do not guess:

```bash
grep -n "^void Preprocess::" src/preprocess.cpp
```

A function ends on the line before the next definition at column 0. That gave us 47–52 and 95–195 exactly.

**Leave these alone.** They look like Livox but are not the external package:

| Location | Why it stays |
|---|---|
| `preprocess.h:115,135,144` | `namespace livox_ros` is defined locally in that same header |
| `preprocess.cpp:482` | uses the local `livox_ros::LivoxPointXyzitl` |
| `laserMapping.cpp:809,810,845,846` | just default topic-name strings, overridden by config |

### 2.3 Trap: nested comment blocks

Running the `sed` block twice — or partially, then again — produces:

```c
/*
/*
void Preprocess::process(const livox_ros_driver2::...)
{ ... } */

*/
```

C++ does not nest `/* */`. The first `*/` closes both, leaving a stray `*/` that is a syntax error. Verify with counts, never by re-running:

```bash
grep -c '^/\*$' src/preprocess.cpp        # want 2
grep -c '^\*/$' src/preprocess.cpp        # want 2
grep -n '^/\*$\|^\*/$' src/laserMapping.cpp   # want one pair, ~311 and ~351
```

If it gets tangled, reset and redo in one pass rather than untangling:

```bash
git checkout -- src/ CMakeLists.txt package.xml
```

### 2.4 Save the patch immediately

The edits were lost twice — once to a `cp` from `.bak`, once to a power cut.

```bash
cd /ouster_ws/src/FAST_LIO
git diff > /ouster_ws/livox_removal.patch     # 148 lines
```

That file lives on the bind mount and survives container restarts and power loss. To restore:

```bash
git checkout -- . && git apply /ouster_ws/livox_removal.patch
```

## 3. Configuration

### 3.1 Create a new file — do not edit `ouster64.yaml`

The stock configs are tracked by git. Editing one puts a permanent diff in the checkout, tangled with the Livox patch. Create `config/ouster32.yaml` instead.

### 3.2 `config/ouster32.yaml`

```yaml
/**:
    ros__parameters:
        feature_extract_enable: false
        point_filter_num: 3
        max_iteration: 3
        filter_size_surf: 0.5
        filter_size_map: 0.5
        cube_side_length: 1000.0
        runtime_pos_log_enable: false
        map_file_path: "./test.pcd"

        common:
            lid_topic:  "/points"
            imu_topic:  "/imu"
            time_sync_en: false
            time_offset_lidar_to_imu: 0.0

        preprocess:
            lidar_type: 3          # 3 = Ouster
            scan_line: 32          # OS-1-32, NOT 64
            timestamp_unit: 3      # nanoseconds
            blind: 1.0             # see below

        mapping:
            acc_cov: 0.1
            gyr_cov: 0.1
            b_acc_cov: 0.0001
            b_gyr_cov: 0.0001
            fov_degree:    360.0
            det_range:     100.0   # OS-1 is ~120 m
            extrinsic_est_en:  false
            extrinsic_T: [ -0.006, 0.012, 0.029 ]
            extrinsic_R: [-1., 0., 0.,
                           0., -1., 0.,
                           0., 0., 1.]

        publish:
            path_en:  true
            scan_publish_en:  true
            dense_publish_en: true
            scan_bodyframe_pub_en: true

        pcd_save:
            pcd_save_en: false
            interval: -1
```

### 3.3 What differs from stock, and why each matters

**`scan_line: 32`** — stock is 64. Wrong beam count corrupts the scan structure.

**`blind: 1.0`** — stock is **4.0**, which discards every return within 4 m of the sensor. That is reasonable for a 64-beam unit on a car roof. On our robot the LiDAR sits at **0.694 m**, so `blind: 4.0` would throw away the ground, nearby obstacles, and lane markings — everything we can actually see. Tune downward if self-returns from the chassis appear.

**`extrinsic_T` / `extrinsic_R`: the IMU→LiDAR transform, and it is NOT identity.**

```bash
ros2 run tf2_ros tf2_echo os_imu os_lidar
# Translation: [-0.006, 0.012, 0.029]
# Rotation RPY (degree): [0, 0, 180]
```

**The 180° yaw is the important part.** The Ouster's IMU and LiDAR frames are rotated half a turn relative to each other. Every stock config assumes identity. Leaving it identity produces odometry mirrored front-to-back, which presents as catastrophic drift rather than as a rotation error.

`extrinsic_R` as a 180° yaw about Z:

```
[-1,  0,  0,
  0, -1,  0,
  0,  0,  1]
```

These values are per-unit. Read them from your own sensor, either via `tf2_echo` or from `169.254.177-metadata.json` (`imu_to_sensor_transform`, `lidar_to_sensor_transform`). Never copy them from a tutorial.

**`pcd_save_en: false`** — with `interval: -1` the stock config accumulates the entire map in RAM and writes on shutdown, which can OOM on long runs. Enable deliberately when a map is wanted.

### 3.4 `--symlink-install` does not pick up new files

Symlinks are created at build time for files present then. A config created afterward will not appear in `install/`:

```bash
ls -la /ouster_ws/install/fast_lio/share/fast_lio/config/   # ouster32.yaml missing
cd /ouster_ws && colcon build --packages-select fast_lio --symlink-install
```

Fast — nothing recompiles, only the install step reruns. Same family as day-1 §7.4.

### 3.5 The launch file default is a trap

```python
declare_config_file_cmd = DeclareLaunchArgument(
    'config_file', default_value='mid360.yaml', ...)
```

**Forget `config_file:=` and FAST-LIO2 starts happily with Livox settings**, subscribes to `/livox/lidar`, receives nothing, and sits silent. No error, no warning — just no output. Always pass it explicitly, and put the full command in a script.

## 4. Trap: QoS mismatch silently starved the filter

The most consequential failure of the day, because it produced a warning rather than an error.

```
[WARN] [laser_mapping]: New publisher discovered on topic '/imu', offering
incompatible QoS. No messages will be sent to it.
Last incompatible policy: RELIABILITY_QOS_POLICY
```

**FAST-LIO2 subscribes to `/imu` as RELIABLE. The Ouster driver publishes as BEST_EFFORT** (sensor-data QoS). A reliable subscriber cannot match a best-effort publisher — a hard incompatibility, not a degradation. FAST-LIO2 was receiving **zero IMU data** and therefore could not produce odometry at all.

**Fix**, in `agv_bringup`'s driver parameter block:

```python
'use_system_default_qos': True,
```

That switches `/points` and `/imu` to default (reliable) QoS, matching what FAST-LIO2 expects.

> **Note this is the same QoS axis as day-2 §3, in the opposite direction.** There, a *remote* reliable subscriber blocked the publisher and caused packet drops. Here, a *local* reliable subscriber could not match a best-effort publisher at all. Reliable is correct now precisely because FAST-LIO2 runs locally on spring and nothing remote subscribes to `/points`. **If a remote subscriber is ever added back, revisit this.**

### 4.1 The `ring` warning is cosmetic

```
Failed to find match for field 'ring'.   (repeated per scan)
```

The field is present:

```bash
ros2 topic echo /points --field fields --once
# ... PointField(name='ring', offset=26, datatype=4, count=1) ...
```

`ring` sits at offset 26, which is not 4-byte aligned, and FAST-LIO2's compiled-in `ouster_ros::Point` struct predates the current SDK layout. Same family as the `WINDOW` crash from day 2 — an SDK/firmware version mismatch.

**It is non-fatal.** Odometry publishes correctly at 10 Hz with the warning present. Ignore it; revisit only if scan quality looks wrong.

## 6. The TF bridge

### 6.1 Why it is needed

FAST-LIO2 publishes `camera_init → body`:

- **`camera_init`** — wherever the robot was at startup. Not connected to anything.
- **`body`** — the **IMU** frame (`os_imu`), not the robot base.
- **Timestamps are an internal counter** starting near zero. Observed `sec: 2615` against a wall clock of `1789571000`. tf2 reads that as 1970 and rejects every lookup.

So three things must be fixed before the pose is usable.

### 6.2 Why `base_footprint`, not `base_link`

**`base_link` already has `base_footprint` as its parent** from the URDF. Publishing `odom → base_link` would give it two parents. tf2 is last-writer-wins, so the robot would flicker between two poses at 10 Hz — worse than the static version of this bug (day-1 §7.2) because it never settles.

`base_footprint` is the tree root and is free to adopt `odom` as its parent.

### 6.3 Why the pose must be composed, not copied

FAST-LIO2's pose describes the **IMU**. Publishing it directly as `odom → base_footprint` would place the robot's ground origin inside the LiDAR, 0.69 m up and 0.285 m forward.

The bridge looks up the static `os_imu → base_footprint` from the URDF (cached once — it is a fixed mounting relationship) and composes:

```
T_odom_base = T_camerainit_body @ T_imu_base
```

### 6.4 Install

`agv_bringup` is an **`ament_python`** package (`setup.py` + `setup.cfg`), not `ament_cmake`. So:

- file goes at `agv_bringup/agv_bringup/fastlio_tf_bridge.py`
- register in `setup.py` under `entry_points`:
  ```python
  'console_scripts': [
      'fastlio_tf_bridge = agv_bringup.fastlio_tf_bridge:main',
  ],
  ```
- ensure `agv_bringup/agv_bringup/__init__.py` exists

Dependencies:

```bash
apt install -y ros-humble-tf-transformations
# pulls in python3-transforms3d automatically — no pip needed
python3 -c "import transforms3d; from tf_transformations import quaternion_matrix; print('ok')"
```

`package.xml` had **no declared dependencies at all**. Added:

```xml
<exec_depend>rclpy</exec_depend>
<exec_depend>nav_msgs</exec_depend>
<exec_depend>geometry_msgs</exec_depend>
<exec_depend>tf2_ros</exec_depend>
<exec_depend>tf_transformations</exec_depend>
<exec_depend>robot_state_publisher</exec_depend>
<exec_depend>ouster_ros</exec_depend>
<exec_depend>xacro</exec_depend>
```

The last three were already used by the launch file and never declared — which is why `rosdep install` would not have caught the missing `xacro` on day 1.

### 6.5 Run and verify

```bash
ros2 run agv_bringup fastlio_tf_bridge     # no .py — it is a console script
```

```
[INFO] Bridging /Odometry (body in camera_init) -> odom -> base_footprint
[INFO] Waiting for static transform os_imu -> base_footprint ...
[WARN] Cannot yet look up os_imu -> base_footprint: ... does not exist
[INFO] Cached os_imu -> base_footprint: [-0.2913, 0.0118, -0.6656]
[INFO] First transform published. Bridge is live.
```

The warning resolves in ~95 ms — the listener started marginally before `/tf_static` arrived, then caught it. Working as designed.

**Sanity-check the cached transform.** `[-0.2913, 0.0118, -0.6656]` inverts the URDF: −0.285 x (LiDAR mount) −0.006 (IMU internal), −0.658 z (base_link height) −0.029 (IMU internal). The 1.18 cm in y comes entirely from the Ouster's internal IMU placement. All factory calibration, appearing exactly where expected.

```bash
ros2 run tf2_ros tf2_echo odom base_footprint
# Translation: [-0.286, -0.012, -0.681]
# Rotation RPY (degree): [-0.08, -0.17, -0.06]
```

**The nonzero offset is correct**, not an error. FAST-LIO2 initialises `camera_init` at the IMU's starting pose; `base_footprint` is 0.68 m below and 0.29 m behind it. The robot is not 68 cm underground — the odom origin is simply at LiDAR height.

Values drifting ~2 mm between samples on a stationary robot is healthy filter noise.

### 6.6 The restamping tradeoff

The bridge restamps with current ROS time, because FAST-LIO2's internal counter is unusable. Cost: up to one cycle of latency error (~100 ms at 10 Hz). Invisible when stationary; up to **12 cm of position error at the robot's 1.18 m/s top speed**.

The better fix is patching FAST-LIO2 to stamp with the input cloud's timestamp. If odometry looks laggy during fast motion, that is where to look. `restamp:=false` tests the alternative once upstream stamping is fixed.

## 10. Next: teleop and bags

### Teleop, on spring's **host** (not the container)

The container has no `nova_teleop`, no `joy`, no device access. Spring's host already has ROS Humble and `ROS_DOMAIN_ID=0`, and the container runs `--network host`, so host and container nodes share one DDS graph.

Findings so far:

- **`/dev/stm1` does not exist on spring** — that alias came from a udev rule on someone else's laptop. The device is **`/dev/ttyACM0`**. Either edit `wireless_teleop.py` or write the udev rule.
- **No `/dev/input/js*`** — gamepad not yet connected or paired.
- Group membership needed: `sudo usermod -aG dialout,input spring`, then **log out and back in**.

**Verify the axis mapping before the wheels touch the ground.** DualSense indices differ between USB and Bluetooth. The node expects `AXIS_L2=2`, `AXIS_R2=5`, `AXIS_L3_X=0`, `AXIS_DPAD_X=6`. Check with `ros2 topic echo /joy` and press each control.

**Safety:** the node slew-limits only D-pad spin. Normal driving uses `step = 1000.0`, so commanded RPM jumps instantly 0 → full. On 37.5 cm wheels with a 78 cm track, that is abrupt. First run with wheels off the ground; ease into the triggers.

**No odometry from teleop.** The serial link is write-only — no encoder readback. FAST-LIO2 is the only odometry source, with nothing to cross-check against. Worth asking the electronics team whether the STM32 can report actual RPM back.

### Recording

**Record raw sensor data, with FAST-LIO2 and the bridge switched OFF.**

```bash
ros2 bag record -o "$(date +%F_%H%M)_drive" \
  /points /imu /tf /tf_static /robot_description /target_rpm
```

Recording `/Odometry` bakes in whatever tuning was active. Raw data lets the whole pipeline be re-run with different parameters as many times as wanted.

Rates measured 2026-09-15: **7.3 MB/s, ~440 MB/min.** 347 GB free — no constraint.

Record on the machine producing the data. Never record spring's `/points` from manas (day-2 §3).

Drive patterns: straight lines, gentle curves, in-place rotations, and **at least one loop returning to the exact start point**. FAST-LIO2 has no loop closure, so the gap between where it thinks the robot ended and where it actually is *is* the drift measurement.

**Short bag first, replayed on the spot.** Discovering a problem after twenty minutes of driving wastes the session.

For replay against FAST-LIO2:

```bash
ros2 bag play <bag> --clock
ros2 launch fast_lio mapping.launch.py config_file:=ouster32.yaml use_sim_time:=true rviz:=false
```
